# IRIS — SOAR Module (Investigation > SOAR)

## Overview

The SOAR module provides an analyst-driven **job orchestration** and management interface inside IRIS. Jobs are manual or program-triggered automation/playbooks that run discrete actions (e.g., quarantine host, run full-disk scan, collect forensic artifacts via Velociraptor). Jobs execute as **Jobs** (immutable execution records) and produce **artifacts** and **audit logs** attached to IRIS cases.

This document outlines the UX, data model, behaviors, and example job templates required to implement the module.

---

## Goals / Non-functional requirements

* Allow analysts to **select, configure, run, and audit** SOAR jobs from within IRIS cases.
* Support manual invocation and programmatic calls (webhook / API / automation triggers).
* Provide flexible **target selection** (agent ID, hostname, IP, tenant, group).
* Provide configurable **notifications** and **artifact storage** destinations.
* Secure operations with RBAC and approval gates for destructive actions.
* Persist complete execution history (inputs, outputs, API responses) to cases for evidence and compliance.

---

## Key Concepts

* **Job Template** — reusable definition of a playbook. Contains metadata, steps (API calls / commands), inputs, prechecks, rollback steps, and expected artifacts.
* **Job Instance / Job Run** — an execution of a Job Template with concrete parameters and targets. Immutable once created; stores status and results.
* **Target** — an object the job acts upon (agent_id, host, asset tag, tenant id). Templates declare allowed target types.
* **Artifact** — files, logs, and JSON outputs generated by a job (evidence attachments stored in IRIS case or external storage).
* **Receiver / Notifier** — where to send notifications (email, Teams/Slack channel, PagerDuty, Webhook).
* **Storage Location** — where generated artifacts are persisted (case attachments, S3, internal file store).
* **Approval Gate** — flag that requires an approver (specified role) to confirm before destructive steps execute.

## SOAR Tab — UI Layout (Investigation > SOAR)

**Header / Context**

* Case header (case id, title, severity, primary analyst) & quick links (open playbooks, view artifacts).
* Quick summary: last SOAR job runs for this case (status summary).

**Left: Job Catalog / Management**

* Searchable list of Job Templates (name, tags, description, owner, last modified).
* Filters: vendor (SentinelOne, Velociraptor), risk level, requires-approval, category (containment/forensics/triage).
* Buttons: `Create Template`, `Edit Template`, `Delete Template` (RBAC gated).

**Center: Job Run / Configuration Panel**

* Selected Job Template expanded with description, steps, inputs, required permissions, and expected artifacts.
* Input fields (auto-populated from case): target selector (dropdown), run-as user, comments, corroboration evidence checklist, storage destination selector, notification list.
* Toggles: `Require Approval`, `Store Artifacts in Case`, `Send Notifications`, `Auto-attach outputs to case`.
* Buttons: `Save & Run`, `Run (as dry-run)`, `Schedule` (optional), `Run via API` (shows curl/webhook).

**Right: Execution Log & Results**

* Live job status (Queued → Running → Succeeded / Failed / Partially Succeeded).
* Step-by-step timeline showing executed API calls with request JSON and response JSON (expandable).
* Artifacts list (download links), job metadata (start/end time, executor, approver if any), and post-run actions (promote artifact to evidence, create follow-up task).

**Modal: Approval Workflow**

* When `Require Approval` is set, a modal is shown requesting approver, reason, and urgency. Approver receives notification with one-click Approve/Reject. Actions are logged.

## Job Lifecycle

1. **Design** — Admin or power user creates a Job Template. Template includes metadata, allowed target types, required permissions, input schema, steps, and artifact definitions.
2. **Prepare** — Analyst selects template (in case context), fills inputs, chooses target(s), notification and storage options. IRIS runs *preflight checks* (agent online, API credentials valid, corroboration checks). Failures prompt warnings and block run unless overridden by permitted role.
3. **Approval** (optional) — If the template requires approval, the job is set to `Pending Approval`. Approver must accept/reject. Approval includes a mandatory comment.
4. **Execute** — IRIS enqueues job into background job runner. Each step executes sequentially (or in defined parallel groups), with retry/backoff rules applied on transient failures.
5. **Collect Artifacts** — artifacts created by steps are downloaded or referenced and attached to the case (or external storage per configuration).
6. **Finalize** — job completes; status and full execution logs are persisted. Notifications are sent. Analyst can promote artifacts to case evidence and create follow-up tasks.
7. **Rollback (optional)** — if defined and chosen, run rollback steps for destructive actions.

## Job Template Structure (JSON Schema)

Below is a suggested JSON schema for storing Job Templates in IRIS.

```json
{
  "id": "uuid",
  "name": "Quarantine + Forensic Grab",
  "description": "Quarantine agent in SentinelOne and run Velociraptor artifact pack",
  "owner": "sec-ops@company",
  "vendor": "SentinelOne",
  "tags": ["containment","forensics"],
  "requires_approval": true,
  "allowed_target_types": ["agent_id","hostname","asset_tag"],
  "inputs": [
    {"name":"agent_id","type":"string","required":true},
    {"name":"case_id","type":"string","required":true},
    {"name":"comment","type":"string","required":false}
  ],
  "prechecks": [
    {"type":"api_check","name":"sentinel1_online","endpoint":"/agents/{agent_id}","assert":"online==true"},
    {"type":"corroboration_check","sources":["otx","abusipdb","vt"],"policy":"1_of_3"}
  ],
  "steps": [
    {
      "id":"step1",
      "name":"Quarantine Host",
      "type":"api_call",
      "vendor":"sentinelone",
      "operation":"agents.actions.disconnect",
      "payload":"{ \"filter\": { \"ids\": [\"{{agent_id}}\"] }, \"networkQuarantine\": true, \"comment\": \"{{comment}}\" }",
      "on_failure":{"action":"halt","retries":1}
    },
    {
      "id":"step2",
      "name":"Fetch S1 Logs",
      "type":"api_call",
      "vendor":"sentinelone",
      "operation":"agents.actions.fetch-logs",
      "payload":"{ \"filter\":{ \"ids\":[\"{{agent_id}}\"] }, \"logTypes\": [\"agent\",\"threat\"] }",
      "outputs":[{"name":"log_job_id","path":"$.job_id"}]
    },
    {
      "id":"step3",
      "name":"Velociraptor Collect",
      "type":"api_call",
      "vendor":"velociraptor",
      "operation":"clients.actions.collect",
      "payload":"{ \"client_id\": \"{{agent_id}}\", \"artifacts\":[\"Windows.System.Processes\",\"Windows.Memory.Dump\"] }",
      "on_failure":{"action":"continue","retries":2}
    }
  ],
  "artifacts": [
    {"name":"s1_logs","type":"json","source_step":"step2","path":"$.results"},
    {"name":"vr_memdump","type":"file","source_step":"step3","path":"$.download_links[0]"}
  ],
  "storage_policy":{
    "store_in_case":true,
    "external_s3":null
  },
  "notifications":{
    "on_success":[{"type":"teams","target":"#soc-ops"},{"type":"email","target":"oncall@company"}],
    "on_failure":[{"type":"pagerduty","target":"PD_ESCALATION"}]
  }
}
```

## Storage & Artifact Handling

* Default: Attach artifacts to the case by adding a new folder in the "Notes" section for each case called <soar-workflow-name / date>. Once the folder is added, the report will "show up" as a file in markdown format in that specific folder

## RBAC, Permissions & Approval

* Map SentinelOne/Velociraptor operations to IRIS roles and require that user role includes required permissions. Example: `quarantine` requires `soar.quarantine` + `sentinelone.disconnect`.
* Approval roles: define one or more roles that can approve (`soar.approver`). Approvals are logged with timestamp and approver id.
* Escalation policy: if approver does not respond within configured timeout, escalate to on-call.

---

## Audit, Compliance & Logging

* Persist every API request and response (full JSON) against the job run. Do not allow deletion of job run logs except by admin with a logged justification.
* Maintain tamper-evident trail (signed records or append-only store) for evidentiary use.
* Provide export of full job run record (JSON + artifacts) for legal/IR requirements.

---

## Error Handling & Retries

* Steps declare `on_failure` behavior: `halt` (stop job), `continue` (mark step failed), or `retry` with backoff and max attempts.
* Transient API errors receive exponential backoff; critical failures (auth, invalid payload) halt and surface to analyst.
* Provide manual `Rerun` and `Resume` actions from UI for failed jobs (with optional new inputs).

---

## API Surface (for programmatic runs)

* `POST /api/soar/jobs` — create & start a job run (returns job_id) (auth: user token + scope `soar.run`).
* `GET /api/soar/jobs/{job_id}` — fetch job run status and logs.
* `POST /api/soar/templates` — create template (admin)
* `GET /api/soar/templates` — list templates
* `POST /api/soar/jobs/{job_id}/approve` — approver endpoint
* `POST /api/soar/jobs/{job_id}/cancel` — cancel a queued/running job
* `GET /api/soar/jobs/{job_id}/artifacts/{artifact_id}` — download artifact

**Webhook trigger**

* IRIS exposes a webhook payload to start a job. Example minimal payload:

```json
{
  "template_id": "uuid",
  "case_id": "IRIS-2025-123",
  "inputs": {"agent_id":"225494730938493804","comment":"Auto-triggered by rule X"},
  "initiator": "automation_rule_42"
}
```

## Acceptance Criteria

* Analyst can select a Job Template, configure inputs, and run a job from the case UI and receive results/artifacts attached to the case.
* Jobs that require approval cannot execute destructive steps until an approver approves.
* All API requests/responses and artifacts are logged and retrievable for audit.
* Notifications are delivered to configured channels on success/failure.
* Jobs can be invoked via API/webhook with proper auth and propagate outputs back into IRIS case.
