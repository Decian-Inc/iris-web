# SOAR Job Reporting System - Implementation Report

## Overview

This document provides a comprehensive overview of the SOAR (Security Orchestration, Automation and Response) job reporting system implemented in IRIS. The system evolved from basic mock data responses to a full enterprise-grade job management platform with persistent storage, approval workflows, scheduling, and advanced analytics.

## Implementation Phases

### Phase 1: Core Job Storage ✅

**Objective**: Replace mock data with persistent database storage for SOAR jobs

#### 1.1 Database Models Created

**SoarJob Model (`source/app/models/soar.py`)**
```python
class SoarJob(db.Model):
    # Core job metadata
    job_id = Column(String(36), primary_key=True)  # UUID
    case_id = Column(Integer, ForeignKey('cases.case_id'))
    template_id = Column(String(50))
    template_name = Column(String(200))
    integration_type = Column(String(50))  # sentinelone, velociraptor, etc.
    target = Column(String(255))
    status = Column(String(20))  # Running, Completed, Failed
    executor_id = Column(Integer, ForeignKey('user.id'))

    # Timestamps
    created_at = Column(DateTime(timezone=True))
    started_at = Column(DateTime(timezone=True))
    completed_at = Column(DateTime(timezone=True))

    # Results and metadata
    result_data = Column(JSONB)  # Full job execution results
    error_message = Column(Text)
    job_parameters = Column(JSONB)  # Job-specific config
    comment = Column(Text)
```

**SoarJobStep Model**
- Tracks individual execution steps within a job
- Stores step order, status, timestamps, and results
- Enables granular progress tracking

**SoarJobArtifact Model**
- Manages file artifacts generated by jobs
- Includes metadata: file size, type, download URLs
- Supports secure file downloads with access control

#### 1.2 Database Migration
**File**: `source/app/alembic/versions/3ed7b2369672_add_soar_job_tables.py`
- Creates all SOAR job tables with proper foreign keys
- Adds performance indexes on frequently queried fields

#### 1.3 Job Execution Integration
**Updated `execute_sentinelone_fetch_apps` function**:
- Creates database job record at execution start
- Tracks 3 steps: Find Agent → Fetch Applications → Save Artifact

#### 1.4 API Endpoints Converted

## System Architecture

### Database Design

**Core Tables**:
1. **`soar_templates`**: Template definitions and metadata
2. **`soar_jobs`**: Main job records with full lifecycle data
3. **`soar_job_steps`**: Granular step tracking within jobs
4. **`soar_job_artifacts`**: File artifact management

**Key Relationships**:
- Jobs → Case (case_id foreign key)
- Jobs → User (executor_id, approved_by foreign keys)
- Steps → Job (job_id foreign key)
- Artifacts → Job (job_id foreign key)
- Templates → User (created_by, updated_by foreign keys)

**Performance Optimizations**:
- Indexed frequently queried fields (status, created_at, case_id)
- JSONB fields for flexible metadata storage
- Proper foreign key constraints for data integrity

### API Design Principles

**RESTful Design**:
- Resource-based URLs (`/soar/jobs`, `/soar/templates`)
- HTTP methods match operations (GET, POST, PUT, DELETE)
- Consistent response formats with `response_success`/`response_error`

**Security**:
- IRIS access control integration (`@ac_api_case_requires`)
- Case-based data isolation
- File download security with existence checks

**Pagination & Performance**:
- Consistent pagination patterns (`page`, `per_page`)
- Query optimization with database indexes
- Efficient filtering without N+1 queries

### Integration Points

**IRIS Core Integration**:
- **Notes System**: Real integration with `app.business.notes`
- **Case Management**: Jobs tied to cases with proper access control
- **User Management**: Executor and approver tracking
- **File Storage**: Artifact storage using IRIS file management

**External System Integration**:
- **Celery**: Job scheduling and background processing
- **SentinelOne**: Example integration with real API calls
- **Logging**: Integration with IRIS logging infrastructure

## Reporting Flow

### Job Lifecycle Reporting

**1. Job Creation**:
```
User creates job → Database record created → Audit log "job_created"
→ If requires approval: Status "Pending Approval"
→ If immediate: Status "Running" + execution begins
```

**2. Execution Tracking**:
```
Job starts → Step records created → Real-time status updates
→ Artifact generation → File storage + database records
→ Completion → Final status update + duration calculation
```

**3. Reporting Data Sources**:
- **Real-time**: Direct database queries for current status
- **Historical**: Time-series analysis from `created_at` timestamps
- **Performance**: Calculated metrics from `started_at`/`completed_at`
- **Audit**: Structured logs in `/var/log/iris/soar_audit.log`

### Analytics Pipeline

**Data Collection**:
1. **Job Metadata**: Stored in `soar_jobs` table
2. **Performance Data**: Calculated from timestamps
3. **Error Data**: Captured in `error_message` fields
4. **User Activity**: Tracked through executor/approver relationships

**Metric Calculations**:
- **Success Rate**: `(completed_jobs / total_jobs) * 100`
- **Average Duration**: `SUM(completed_at - started_at) / COUNT(completed_jobs)`
- **Template Performance**: Aggregated by `template_id`
- **Trend Analysis**: Grouped by time periods

**Report Generation**:
- **On-demand**: API endpoints calculate metrics in real-time
- **Cached**: Future enhancement could add Redis caching
- **Scheduled**: Could integrate with IRIS reporting system
